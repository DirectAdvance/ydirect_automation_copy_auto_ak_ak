> Цель — научить `/direct/autorules` видеть и оптимизировать уже созданные наборы посевов
> (Telegram/Max, `GdPostCampaign`, Grid-only): расход → воронка, площадки. **Картинки/креатив-уровень
> и автосоздание — вне скоупа**, см. «Отложено».

## 0. Текущее состояние (факт по коду, зафиксировано в сессии 2026-07-21)

### Автоправила (`/direct/autorules`, `direct-autorules.service` :5027)
- Код: `autorules_main.py`, `routes_autorules.py`, пакет `autorules/` (`repository.py`, `rules_engine.py`, `corrections.py`, `queries.py`, `placements.py`, `copy.py`, `autorules/sensors/*`).
- Модель правила (`direct_autorules.rules`): `condition_json` (метрика spend/cpa/drr/clicks/cr/impressions/ctr + оператор) + `action_json` (notify/pause_campaign/resume_campaign/change_bid/change_budget/add_negative/add_excluded_site/change_adjustment) + `mode` (manual/auto) + `schedule` + `status` + `account_login`.
- **Поле `schedule` НИКЕМ не читается — планировщика/крона нет.** Правило исполняется только по ручному `POST /api/ar/rules/dryrun` из UI.
- `_AUTO_EXEC_ENABLED = False` — автозапись действий в кабинет жёстко заблокирована кодом.
- Все существующие action-исполнители работают через **Direct API v5** — на Grid-only посевы (`GdPostCampaign`) физически не действуют, нужны свои Grid-исполнители.
- 6 read-only сенсоров (`autorules/sensors/`): anomalies, balance, campaign_status, goals, minus, url_check — 4 из них через Direct API **v5** (посевы не увидят).

### Уже созданные посевы (`create_set_tp8_10.py`, движок вне этого плана — трогать не будем)
- Технически: 3 Grid-мутации подряд (`AddCampaigns → AddPostAdGroups×N → AddPostAds×N`), N = число картинок (1-3). Бюджет/ставка фиксированы в коде (`POST_BUDGET_SUM=10000`, `POST_BID=200`).
- **Все наборы создаются в draft** (`save_draft=True` зашито жёстко). Механизма перевода draft→live в коде НЕТ.
- ⚠️ **Красный флаг для всего плана оптимизации:** если draft-кампании не переводятся в боевой режим НИКАК (ни вручную, ни автоматически) — они не откручиваются, не тратят бюджет, не дают ни расхода, ни площадок, ни лидов. Тогда оптимизировать физически нечего, пока не решён вопрос активации. Это не подтверждено и не опровергнуто фактом — первое, что нужно проверить (см. Фазу -1).
- **Grid-only** — тип `GdPostCampaign`, невидим Direct API v5.
- Контент генерится LLM (M3) один раз при создании, механизма обновления нет.

### Проверено фактом в БД (Victory, `public.yandex_direct_manager_reports`, 2026-07-21)
- Расход по Директу в big_analytics_v5 приходит **только** из этой таблицы (внешний FDW-сервис, код вне репозитория) → `step1` → `raw_yandex` → `step3` → `big_analytics_direct` → `_move_tp8_to_crop()` для `tp IN ('tp8','tp9','tp10')` → `big_analytics_crop_targeting` → `big_analytics_full`.
- Колонка `Placement` **есть и хорошо заполнена** (99.99% строк за 30 дней, ~14k уникальных значений) — но для **старых** обычных Direct-РСЯ кампаний с tp8/9/10-неймингом (другая сущность, не Grid-посевы).
- `AdNetworkType` в таблице — только 2 значения («Сети», «Поиск», словарь v5 Reports). Третьей категории под Grid-посевы нет.
- **Вывод:** таблица заполняется строго через v5 → `GdPostCampaign` **скорее всего не виден** этому источнику. Не подтверждено окончательно — нужна проверка по `CampaignId` реального созданного набора (следующий шаг).

## 2. Фазы

**Фаза -1 — САМОЕ СРОЧНОЕ: жив ли вообще объект оптимизации**
Проверить факт: переводятся ли сегодняшние draft-наборы посевов в боевой режим (вручную оператором в UI Директа/Grid, или как-то ещё)? Если НЕТ ни одного живого набора — оптимизировать нечего, и первая реальная задача — не «оптимизация», а «активация» (см. Фазу 2). Проверяется без кода: посмотреть в кабинете Директа/Grid статус реально созданных ранее наборов.

**Фаза 0 — снять развилку видимости данных**
Найти `CampaignId` реального созданного набора (лучше уже переведённого в live, если такие есть по Фазе -1) и проверить SQL-запросом, есть ли по нему строки в `yandex_direct_manager_reports` (расход, Placement). Разовый read-only факт → `anton_sql` / MCP `postgres-victory`.
- Если **видно** → Фаза 3a (дёшево, дальше почти всё бесплатно через pipeline).
- Если **не видно** → Фаза 3b (дорого, отдельный сборщик).

**Фаза 1 — планировщик автоправил (инфраструктурный долг, независим от Фазы 0)**
`schedule` в БД мёртв — нужен периодический процесс (systemd timer / встроить в существующий digest.service), который проходит активные правила `mode=auto`, гоняет dry-run, для «безопасных» action (notify) шлёт алерт сразу, для остальных — копит на подтверждение (переиспользовать паттерн `confirmed=true` из `/api/ar/adjust`).

**Фаза 2 — Grid-исполнители действий для посевов (замена/дополнение к v5-actions)**
Все текущие action-типы автоправил работают через v5 и посевы не видят/не трогают. Нужны Grid-эквиваленты под конкретные рычаги оптимизации:
- `activate_posevy` (draft→live) — **вероятно самый ценный и срочный**, раз механизма активации нет вообще (см. Фазу -1).
- `pause_posevy` / `resume_posevy` — Grid-аналог pause_campaign/resume_campaign.
- `change_budget_posevy` — Grid-аналог change_budget (сейчас бюджет фиксирован в коде создания).
- `exclude_placement_posevy` — Grid-аналог add_excluded_site (если Grid API вообще позволяет исключать конкретный канал/паблик — нужно проверить отдельно, не факт что применимо к Telegram/Max).

**Фаза 3a (если FDW видит GdPostCampaign)**
Зафиксировать нейминг Grid-кампаний под regex `tp\d+_(cpc|cpa)_(site|kviz|quiz)` → `_move_tp8_to_crop()` подхватит автоматически → расход/воронка/площадки появляются без новой разработки в big_analytics_v5.

**Фаза 3b (если FDW не видит)**
Отдельный сборщик расхода/площадок для `GdPostCampaign`, по аналогии с step10 (посевы Telega.in — расход тянется отдельным API, не из Директа). Полноценная разработка на стороне big_analytics_v5 (`oleg_programmer`), не конфигурация.

**Условия триггеров правил оптимизации** (после того как данные и исполнители готовы): например «spend > X без конверсий за N дней → pause_posevy», «площадка даёт 0 конверсий при спенде > Y → exclude_placement_posevy», «набор в draft дольше суток → notify/`activate_posevy`».

**Безопасность запуска** — первая версия любого нового action-типа: `mode=manual` + notify-алерт с подтверждением, не сразу `auto_exec` (`_AUTO_EXEC_ENABLED=False` и так это блокирует по умолчанию). Расширять на автопилот только после недели наблюдений за предсказуемостью.

## Отложено / вне скоупа
- **Автосоздание новых наборов посевов** — решение Семёна 2026-07-21: не делаем, оптимизируем только созданное.
- **Показатели по изображениям/креативам** — ни big_analytics_v5, ни текущая Grid-интеграция этого не дают. Если понадобится — отдельная задача: разведка, есть ли в Grid GraphQL статистика на уровне `AddPostAds` (объявление = картинка).
